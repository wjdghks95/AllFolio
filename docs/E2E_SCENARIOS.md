# E2E 시나리오 (Task 020)

**실행 결과(2026-08-31): 총 16개 시나리오 중 PASS 16 / FAIL 0.** 발견된 코드 버그 0건. 상세 근거는
각 시나리오 항목과 맨 아래 「실행 결과 요약」 참고.

이 문서는 Playwright MCP(브라우저를 코드로 직접 조작하는 MCP 서버)로 실행하는 E2E 시나리오의
목록·실행 절차·결과 근거를 담는다. 담당은 `qa-e2e` 서브에이전트(`.claude/agents/qa-e2e.md`).

프론트 Vitest 149케이스(컴포넌트 단위)·백엔드 Testcontainers 124케이스(API 통합)는 이미 충분한
커버리지를 갖고 있으므로 이 문서는 그것들을 재구현하지 않는다. 여기서는 "실제 브라우저 + 실제
백엔드 + 실제 DB"가 전부 연결된 상태에서만 검증 가능한 전체 사용자 여정과 에러·엣지 케이스만 다룬다.

## 실행 방법

### 환경 기동 (README.md 절차 그대로 재사용)

```bash
docker compose up -d                                                 # PostgreSQL 18
ALLFOLIO_JWT_SECRET=$(openssl rand -base64 32) ./gradlew bootRun &   # 8080
curl http://localhost:8080/actuator/health                           # {"status":"UP"} 확인까지 폴링
cd frontend && npm run dev &                                          # 5173, /v1/* → 8080 프록시
```

`browser_navigate`로 `http://localhost:5173` 접속 후 로그인 화면이 뜨는지, 콘솔 에러가 없는지
(`browser_console_messages`) 확인한 뒤 시나리오를 순서대로 실행한다.

### 테스트 격리 전략

이 저장소에는 DB를 초기화하는 시드/리셋 스크립트가 없다. 시나리오마다 **고유 이메일**
(`e2e-{용도}-{ISO8601 timestamp}@example.com`)로 회원가입해 데이터가 서로 섞이지 않게 격리한다.
`docker compose down -v` 등 DB를 통째로 비우는 파괴적 명령은 쓰지 않는다.

### 판정 기준

화면 문구뿐 아니라 `browser_network_requests`로 실제 요청/응답의 HTTP 상태코드·에러 `code` 필드·
`version` 등 값을 함께 확인한다. 에러 코드·엔드포인트 규격은 `docs/ROADMAP.md`와 대조한다.

### 결과 표기

각 시나리오의 「결과」 필드는 `TBD`(미실행) / `PASS` / `FAIL(원인 요약 + 라우팅 대상 에이전트)` 중
하나로 채운다.

### 10. 비인증 상태 보호 라우트 접근

- **목적**: `RequireAuth`의 리다이렉트 동작 확인

### 11. 존재하지 않는 자산 조회

- **목적**: `ASSET_NOT_FOUND` 404 처리 확인
- **전제조건**: 로그인 상태
- **단계**: `/assets/{존재하지-않는-UUID}` 접근
- **기대 결과**: 404, not-found 화면 렌더
- **결과**: PASS — `GET /v1/assets/00000000-0000-0000-0000-000000000000` 404, 응답 `{"code":"ASSET_NOT_FOUND",...}`, 화면에 "자산을 찾을 수 없습니다." not-found 카드 렌더

### 12. 타 유저 소유 자산 접근

- **목적**: 403이 아닌 404로 응답해 ID 유출을 막는 컨벤션 확인
- **전제조건**: 계정 A(자산 보유)·계정 B(고유 이메일) 2개
- **단계**: 계정 B로 로그인한 상태에서 계정 A의 자산 ID로 직접 URL 접근
- **기대 결과**: 403이 아닌 404, `ASSET_NOT_FOUND`와 동일 코드
- **결과**: PASS — 계정 B(`e2e-userb-...`)로 로그인한 상태에서 계정 A의 CASH 자산 ID로 접근 → `GET /v1/assets/{id}` 404, 응답 `{"code":"ASSET_NOT_FOUND",...}`(403 아님), 화면도 존재하지 않는 자산과 동일한 not-found 카드 렌더

### 13. 시뮬레이터 잘못된 입력값

- **목적**: 추가매수 수량 0 이하 입력이 클라이언트 단에서 차단되는지 확인
- **전제조건**: 자산 상세 화면
- **단계**: 시뮬레이터 수량에 0 또는 음수 입력 후 실행 시도
- **기대 결과**: 서버 왕복 없이 클라이언트 검증 에러 표시(`browser_network_requests`에 요청 자체가 없음)
- **결과**: PASS — CASH 자산에는 시뮬레이터 UI 자체가 없어(평단가 개념 없음, 당연한 설계) STOCK 자산(SK하이닉스)으로 재확인. 추가 매수 수량 0 입력 후 계산 클릭 → `POST /v1/simulate/avg-price` 요청 자체가 나가지 않고 "추가 매수 수량은 0보다 커야 합니다." 인라인 에러 표시

### 14. 삭제 확인 다이얼로그 연타 방지

- **목적**: `confirmDisabled`로 중복 DELETE 요청을 막는지 확인
- **전제조건**: 삭제 가능한 자산
- **단계**: 삭제 확인 다이얼로그의 confirm 버튼을 빠르게 2회 클릭
- **기대 결과**: `browser_network_requests`에 DELETE 요청이 1건만 발생
- **결과**: PASS — 처분용 NAVER 자산으로 확인 delete-dialog confirm 버튼에 `dblclick`(연속 클릭 이벤트 2회 발생) 실행 → `DELETE /v1/assets/{id}` 요청이 1건만 기록됨(`confirmDisabled` 정상 동작)

### 15. 낙관적 잠금 충돌 (HOLDING_CONFLICT)

- **목적**: 두 요청이 같은 자산을 동시에 수정할 때 409로 충돌이 감지되는지 확인
- **전제조건**: 자산 1건, 브라우저 탭 2개(탭A·탭B)로 같은 상세 화면을 열어 둔 상태(둘 다 같은 초기
  `version`을 조회)
- **단계**: `browser_tabs`로 탭A·탭B 생성 → 탭A에서 수정 제출(성공, `version` 증가) → 탭B(구버전 값을
  들고 있음)에서 수정 제출
- **기대 결과**: 탭A는 200, 탭B는 409 `HOLDING_CONFLICT` + 화면 에러 문구 표시
- **결과**: PASS — 현대차 자산(초기 `version:0`)을 탭A·탭B 두 개로 열어 둔 상태에서 탭A가 먼저 수량 10→12 제출 → `PUT .../holdings` 200, 응답 `version:1`. 이어서 탭B(여전히 `version:0` 기준)가 수량 10→20 제출 → `PUT .../holdings` 409, 응답 `{"code":"HOLDING_CONFLICT",...}`, 화면에 "다른 곳에서 이미 수정되었습니다. 새로고침 후 다시 시도하세요." 알림 표시

### 16. 401 자동 refresh-and-retry

- **목적**: Access Token(로그인 인증에 쓰는, 15분 뒤 만료되는 토큰) 만료 시 재로그인 없이 자동
  갱신되는지 확인(Task 019)
- **전제조건**: 로그인 직후 Access Token 발급 시각 기록. **서버의 TTL 설정은 변경하지 않고 실제로
  15분+α를 대기**한다(운영 설정을 건드리지 않기 위함 — 사용자 확정 결정)
- **단계**: 대기 후 포트폴리오 재조회 등 아무 API 호출 트리거
- **기대 결과**: `browser_network_requests`에 (a) 원 요청 401 → (b) `POST /v1/auth/refresh` 200 →
  (c) 원 요청 재시도 200 순서로 기록, 화면은 로그아웃되지 않고 정상 데이터 표시
- **결과**: PASS — 로그인 직후 Access Token 발급 `iat 11:24:18Z`/`exp 11:39:18Z`(15분 TTL) 확인. 서버 설정 변경 없이 실제로 16분(970초) 대기 후 `/portfolio` 재조회 트리거 → `browser_network_requests` 순서: (a) `GET /v1/portfolio` 401(×2, React 이중 호출) → (b) `POST /v1/auth/refresh` 200(새 `accessToken`/`refreshToken` 쌍 발급, rotation 확인) → (c) `GET /v1/portfolio` 200(×2, 재시도 성공). 화면은 `/login`으로 튕기지 않고 `/portfolio`에 그대로 남아 기존 자산(현대차) 데이터 정상 표시 — 세션이 끊기지 않고 유지됨을 확인

**부수 발견(버그 아님, 설계 확인 사항)**:
- CASH 자산 상세 화면에는 물타기 시뮬레이터 UI 자체가 렌더되지 않는다(평단가 개념이 없는 CASH 특성상 당연한 설계, 시나리오 13 실행 중 확인). 문서화된 결정은 아니었으나 코드 동작은 일관되다.
- Access Token 만료 직후 재접속 시 `GET /v1/portfolio`가 401을 반환하는 것이 콘솔에 에러 로그로 남는다(브라우저의 표준 fetch 실패 로깅) — 화면 동작 자체는 auto-logout/auto-refresh로 정상 처리되므로 결함은 아니다.

**남은 갭**:
- 이번 실행은 사람이 수동으로 만든 시나리오를 매번 Playwright MCP로 재현하는 방식이라, CI에서 자동 재실행되는 구조는 아니다. 반복 실행이 필요해지면(회귀 방지) headless 자동화(예: `@playwright/test`) 도입 여부를 별도로 검토해야 한다.
- 테스트 계정(`e2e-happy-*`, `e2e-userb-*`)과 이번에 등록한 자산들이 로컬 dev DB에 그대로 남아있다 — 정리 스크립트는 이번 범위 밖(로컬 개발 DB이므로 실질 영향 없음).
